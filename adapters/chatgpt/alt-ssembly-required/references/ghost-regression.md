# Ghost in the Loop — Regression Case for Alt-ssembly Required

Use this as a red-team fixture when repairing Ghost or validating Alt-ssembly against a similar browser/userscript product.

## Historical failure probes

1. **Transport overcorrection** — A Play/Send repair must not delete skins, sound, notifications, personas, workflows, settings, richer export, or other accepted surfaces outside the authorized delta.
2. **Operator correction** — If the owner says “simplify controller/send logic only,” the Product Packet must change immediately. Repeated broader rewrites are process failure.
3. **Field-vs-synthetic** — Unit/fixture/browser automation cannot certify authenticated Firefox Android/Tampermonkey when that exact path is load-bearing.
4. **Host mutation** — Composer/editor nodes may be replaced after insertion. Verify the live current node and user-visible state, not a stale reference.
5. **At-most-once actuation** — Ambiguous Send authority must fail closed. Do not escalate blindly through click/requestSubmit/Enter after an uncertain actuation.
6. **Parallel-state reconciliation** — Multiple branches/chats/handoffs must converge into one candidate from current repo truth before release.
7. **Stale-test authority** — A test expecting an obsolete UI toggle must not force obsolete architecture back into the product.
8. **Export completeness and language** — Prefer platform-native/API conversation data where available; DOM/page scrape is a truthful fallback. User-facing labels must explain the limitation in plain language rather than say `DOM partial`.
9. **Mobile usability** — A handler technically firing is insufficient if the panel covers the screen or controls are too small to operate comfortably.
10. **Opportunity discovery** — For the original product idea, actively inspect adjacent workflows, platform capabilities, open-source patterns, and product surfaces so useful features are discovered before months of piecemeal requests.
11. **Evidence invalidation** — Any change after field proof invalidates affected proof for the changed artifact.
12. **Operator brevity** — Keep detailed diagnostics durable, but tell the owner primarily whether it is fixed, what failed, and what happens next.

## Ghost-specific activation

When asked to repair Ghost:

1. Read current GitHub/main/active branch state first.
2. Build a Product Packet separating `CORE TRANSPORT` from `PROMPT/PROTOCOL`, `UI/PREFERENCE`, `DATA/EXPORT`, `PLATFORM ADAPTER`, `DIAGNOSTIC`, and `PACKAGE/RELEASE`.
3. Protect all accepted non-transport surfaces by default.
4. Treat one Send path as the actuation authority; any uncertainty fails closed.
5. Require exact host/browser/auth/userscript-manager field proof before claiming that field path fixed.
6. Keep export/API work separate from Play actuation.
7. Run the Opportunity Sweep before declaring the rebuilt product feature-complete.
8. Return a short Assembly Receipt and preserve detailed evidence in GitHub artifacts.
